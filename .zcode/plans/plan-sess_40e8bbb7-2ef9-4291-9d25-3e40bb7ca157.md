# Gestion des comptes SchoolFlow — clôture des lacunes (backend + UI)

## Contexte
Le backend implémente déjà ~90 % de l'architecture cible : `UserProvisioningService` (mots de passe temporaire affichés une seule fois, `mustChangePassword`, reset, suspend/disable/archive, verrouillage, révocation de sessions), `ActivationCode` + route publique `/api/activation/activate`, RBAC par permissions avec scope par affectations, audit logging. Les lacunes : le login n'utilise pas la logique de verrouillage, `POST /teachers` contourne le provisioning (mot de passe en clair envoyé par le client), pas de permissions granulaires `users.create.*`, connexion email uniquement, pas de lien inscription→compte, et **aucune interface frontend** pour toute cette API.

## Phase 1 — Backend (`server/src`)

**1. Brancher le verrouillage sur /login** (`routes/auth.ts`)
- Utiliser `isLoginAllowed(user)` (couvre suspended/disabled/archived/locked) au lieu du simple `isActive`
- Échec de mot de passe → `registerFailedLogin(user.id)` ; succès → `clearFailedLogins(user.id)` + mise à jour `lastLoginAt`

**2. Connexion par identifiant** (`routes/auth.ts` + `UserProvisioningService.ts`)
- `/login` accepte email OU username (lookup `Op.or` sur `email` / `username`, validation `.notEmpty()` au lieu de `.isEmail()`)
- Au provisioning : générer un identifiant (ex. `j.kabeya` pour le staff, matricule sans tirets `SCF001245` pour les élèves) avec unicité vérifiée

**3. Refactorer la création d'enseignant** (`routes/teachers.ts` POST /)
- Remplacer le `User.create` direct par `createStaffAccount({ role: 'teacher', ... })` : plus de mot de passe envoyé par le client, `mustChangePassword: true`, retour du mot de passe temporaire **une seule fois**, `logAudit`

**4. Permissions granulaires de création** (`utils/permissions.ts` + `routes/users.ts`)
- Ajouter au catalogue : `users.create.staff`, `users.create.teacher`, `users.create.student`, `users.create.parent`
- Appliquer : POST `/users` → `users.create.staff` (rôle teacher → exige en plus `users.create.teacher`) ; `/users/student/:id` → `users.create.student` ; `/users/parent/:id` → `users.create.parent`
- Accorder par défaut à admin/super_admin via `LEGACY_ROLE_PERMISSIONS` + seed

**5. Lien inscription → compte** (`routes/students.ts` POST /)
- Accepter `createAccount: 'none' | 'now' | 'activation_code'`
- `now` → `createStudentAccount`, retour identifiant + mot de passe temporaire une fois
- `activation_code` → création d'un `ActivationCode`, retour du code en clair une fois
- Matricule au format `SCF-<année scolaire>-<NNNNN séquentiel par année>` ; les matricules existants restent inchangés

**6. Durcissement de l'activation publique** (`routes/activation-codes.ts`)
- Pour les élèves : vérifier matricule + date de naissance en plus du code

## Phase 2 — Frontend (`client/src`)

**7. Nouvelle page admin `Users.tsx`** (route `/app/users`, entrée sidebar « Utilisateurs »)
- Liste avec recherche, filtres statut/rôle, colonnes : nom, email/identifiant, rôles, statut (badge), dernière connexion
- Modal création de compte staff (compte + infos perso + affectations classes/matières + rôles) → écran de résultat affichant identifiant + mot de passe temporaire une seule fois (boutons copier)
- Actions par ligne : modifier, suspendre/désactiver/réactiver/archiver (avec raison), réinitialiser mot de passe (temp affiché une fois), révoquer les sessions, voir les sessions actives, gérer les rôles
- Onglet « Codes d'activation » : liste, créer (code affiché une fois), révoquer

**8. Page publique `Activate.tsx`** (route `/activate`, lien depuis Login et Landing)
- Formulaire code + email + nouveau mot de passe → `POST /api/activation/activate` → redirection vers `/login`

**9. Changement de mot de passe forcé**
- À la connexion, si `mustChangePassword` → modal bloquant appelant `/auth/change-password` (le backend re-émet un token) ; blocage de la navigation tant que non changé

**10. `Teachers.tsx`** : supprimer le champ mot de passe, afficher le mot de passe temporaire retourné une fois

**11. `Students.tsx`** : après création, dialogue « Créer le compte élève ? » → Maintenant (affiche identifiant + mdp temp) / Code d'activation (affiche le code) / Plus tard

## Phase 3 — Vérification
- `npm run typecheck` + `npm test` côté server, build côté client
- Démarrage du serveur et smoke-test des flux : création staff → login identifiant → changement forcé → reset → activation élève par code
